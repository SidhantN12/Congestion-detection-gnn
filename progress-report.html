Design used: gcd (~600 cells), Nangate45 Phases complete: 0–8 of 8 Scope: pipeline validation, not a benchmark result
Phase 08

Modern chips are laid out in stages: first the components (transistors, logic gates) are placed on the die, and only afterward are the microscopic wires connecting them actually routed. Routing can fail in specific spots when too many wires need to pass through too little space — this is called congestion, and normally you only find out about it by running the (slow) routing step. This project trains a graph neural network to look at a chip before routing and predict where congestion will happen, directly from the placed components — skipping the expensive routing step entirely. Before scaling up to a large benchmark, the whole pipeline is being validated end-to-end on a tiny, fast test design. Below is what that validation covered, phase by phase.

Before the phase log: what the model actually sees, and how it's graded

Two pieces of vocabulary come up constantly below — what goes into the model, and how a finished prediction gets scored. Worth defining once, up front, rather than re-explaining inline every time.

The input: three kinds of nodes

Graph neural networks don't take an image or a table — they take a graph: a set of nodes, each carrying its own list of numbers, connected by edges. The chip layout gets converted into exactly that, with three kinds of nodes:

Node typeHow manyWhat it carries (its features)
cell 606–607 One per placed component: width & height, pin count (how many wires touch it), and x/y position on the chip.
net 631–632 One per wire (a "net" connects one output to one or more inputs): fanout (how many components it touches), wire span (how far its furthest-apart connections are), and the shape of the rectangle spanning all its connections.
gcell 144–289 One per small grid tile the router divides the chip into: how densely packed with components that tile is, how many wire-endpoints sit in it, and how much wiring room exists there in each of two directions — known before routing runs, since it depends only on the manufacturing layer stack, not on how wires end up drawn.

Four kinds of connection tie these together: which components sit on which wires, which tile each component physically sits in, which components are geometrically close to each other (nearest 8, regardless of whether they share a wire), and which tiles neighbour each other on the grid.

Every measurement is relative to the manufacturing grid, never a raw physical distance — a component is "2 placement-slots wide," not "0.38 micrometres" — so the same trained model could in principle carry over to a different manufacturing process without starting from scratch. Untested here, but the reason for the choice.

The metrics: how a prediction gets graded

Spearman correlation
Ignores the exact predicted number and asks only: did the model get the order right? If it says tile A is worse than tile B, is that actually true? 1.0 = perfect ranking, 0 = no better than guessing, negative = backwards. A model that's consistently off by a fixed amount still scores perfectly here, since the ranking is unaffected — which fits how this is actually used: knowing where to look first matters more than the exact number.
Kendall's τ (tau)
Answers the same underlying question as Spearman — is the ranking right — but counts it differently: it directly tallies how many pairs of tiles got their relative order right versus wrong, rather than comparing rank positions. Somewhat more conservative, less swayed by one or two large rank jumps. Reporting both gives a fuller picture than leaning on either alone.

Not the same as the loss numbers that appear in training curves (Huber + a pairwise ranking loss) — those are what the model optimises while learning; Spearman and Kendall are how its finished predictions get judged afterward. Related in spirit (the ranking loss directly targets rank correctness, same as these metrics measure) but serving different purposes.

2

Extracting the "ground truth" congestion data

Complete

A chip's surface is divided into a grid of small tiles for routing purposes, called GCells. For each tile, the router knows how much wiring capacity is available versus how much is actually used. That's exactly the signal the neural network needs to learn to predict, so a script was written to pull it out of OpenROAD's internal database into a plain numeric array.

To make sure the numbers were actually right — not just plausible-looking — they were checked against OpenROAD's own built-in congestion visualization for the identical chip.

Confirmed

144/144 grid tiles matched OpenROAD's own display to within 0.000005% (floating-point noise)

3

Manufacturing a genuinely congested test case

Complete

A chip this small has far more wiring capacity than it needs, so it never naturally becomes congested — not a useful example for training an AI to spot congestion. Four ways of deliberately provoking it were tried, roughly in order of expected effect: restricting which metal layers wires are allowed to use, packing components in more tightly, shrinking the chip's usable area, and physically blocking off a strip of the chip from being wired through at all.

The first three, on their own or combined, made no meaningful difference — the router is good enough to route around a shortage by using whatever room is left elsewhere. Only the explicit block forced a genuine, unavoidable bottleneck.

Result

64.4% of grid tiles pushed past 90% congestion · peak demand 64% over capacity in the blocked strip

Worth stating plainly: this contradicts the naive assumption that restricting wiring layers alone would be the biggest lever — it wasn't, and that's a real finding, not an inconvenience to smooth over.

Turning the chip layout into the AI's input format

Complete

Graph neural networks operate on graphs, not images or tables — so the chip layout was converted into one, with three kinds of nodes: components, wires (nets), and grid tiles (GCells). Connections capture which components sit on which wires, which tile each component physically sits in, which components are near each other, and which tiles neighbour each other.

The resulting graph was then checked for structural mistakes — the kind that would silently sabotage training later, like a wire connected to nothing, or a tile disconnected from the rest of the grid.

Confirmed

606 component nodes · 631 wire nodes · 144 tile nodes
0 wires with no component connected · 0 tiles disconnected from their neighbours

5

Checking the AI's grid lines up exactly with the congestion data

Complete

Phase 4's grid tiles and Phase 2's congestion data are supposed to describe the exact same physical squares on the chip — if tile #47 in one didn't mean the same physical location as tile #47 in the other, every downstream prediction would be silently, invisibly wrong. This was flagged from the start as the single likeliest place for a bug that produces plausible-looking nonsense rather than an obvious crash, so it got two independent checks rather than one.

First, the exact arithmetic used to assign a component to a tile was checked against OpenROAD's own internal version of that same calculation, for every component in the chip plus several deliberately awkward edge cases (component sitting exactly on a tile boundary, in the odd-sized tile at the chip's far edge, and so on). Second, component positions, tile boundaries, and the congestion heatmap were all plotted together on one image, using a chip layout from Phase 3 that had an obvious congestion hotspot — so a misalignment would be visually obvious, not something that could hide in a uniform chip.

Confirmed

0 mismatches across 614 components + 6 boundary cases · every component's real position falls inside its assigned tile · the known hotspot lines up exactly with the tile rows it should

6

Building a small training set from varied layouts

Complete

A neural network needs more than one example to learn from. The plan was to take the same chip design and re-run placement 30–50 times with three things varied each time — how tightly components are packed, how much of the wiring is deliberately blocked off, and a random seed — so every run produces a genuinely different layout with its own congestion pattern.

Two of those three levers turned out not to work as planned, and both were caught by checking the actual numbers rather than trusting that "the script ran without an error" meant the data was good.

False start 1

The first sweep varied packing density, wiring-layer restriction, and seed. 30 of the 45 runs it produced turned out to have byte-for-byte identical congestion results despite genuinely different component placements underneath — the layer restriction, it turned out, dominates the result so completely that density and seed stop mattering once it's applied. Caught by comparing files directly, not by eyeballing a chart.

False start 2

Swapped the layer restriction for something already proven to work in Phase 3 (an explicit wiring blockage) and re-ran. This time packing density itself turned out to be the dead lever: every density value from loosely-packed to tightly-packed produced the exact same final component positions, because this chip has so much spare room that the density target never actually has to be honoured. Confirmed directly by comparing raw component coordinates between runs, not just the congestion output.

The working formula: the same proven wiring blockage, varied in where it sits and how wide it is, crossed with 5 random placement seeds — both levers independently confirmed to produce real, physically-sensible differences (a wider blockage reliably makes things more congested, not less) before committing to the full run.

Result

45/45 layout variations succeeded · 0 duplicate congestion results (the false-start problem, fully resolved) · every sample shows real overflow (peak demand 46–75% over capacity) · wider blockage reliably means more congestion, in a clean straight-line relationship

7

Confirming the model can learn anything at all

Complete

Before trusting any real training run, a cheaper and more revealing test comes first: can the model perfectly memorise a single example? If it can't, the problem isn't "needs more data" — something upstream is broken (bad features, a mis-built graph, a buggy loss function), and no amount of additional training will fix that. This is a deliberately narrow test, not an attempt to build a usable predictor yet.

The network itself: each node type gets its own small entry layer, then three rounds of message-passing where every node updates itself based on its neighbours (a different learned rule per connection type, so "which wire is this component on" and "which components are nearby" get treated differently, as they should), finishing with a small prediction head reading out two congestion numbers per grid tile. Trained with the two losses mentioned above — Huber plus the pairwise ranking loss — on one moderately-congested layout from Phase 6, chosen deliberately rather than picking the easiest case.

Result

Spearman 0.970 (horizontal) / 0.981 (vertical) · both comfortably above the 0.95 pass bar · converged smoothly over ~350 training passes, no upstream debugging needed

The predicted and actual heatmaps for this one sample are visually almost indistinguishable — exactly what "memorised" should look like.

8

Building a viewer to see the results

Complete

A small interactive app: pick any of the 45 layouts, see predicted congestion next to the real thing on a shared colour scale plus a signed error map, read off Spearman/Kendall scores, and click into the 20 most congested tiles for a close-up comparison.

The app is upfront about a real limitation rather than hiding it: the model behind it is the Phase 7 one — trained on exactly one layout. Switching the viewer to any of the other 44 samples shows that honestly: Spearman drops from ~0.97 on the training sample to roughly 0.4–0.5 elsewhere, which is the expected, unsurprising result of training on a single example with no chance to learn what actually generalises. Training a model that works well across layouts would be a real next step, not something this phase claims to have done.

Confirmed

Re-prediction time: 26.8 ms (gate required under 1,000 ms) · app verified to run with zero errors, including after switching samples, using Streamlit's own automated testing tool
